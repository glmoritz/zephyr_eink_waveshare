## What Was Proven

### E-paper refresh path

- The slow wall-clock time in panel updates is real, but it is not a CPU hot-spin loop.
- The custom SSD16xx driver waits on BUSY using `k_msleep(5)` between checks.
- That means the thread mostly sleeps while the panel waveform runs.
- Relevant file:
  - `src/display_ssd16xx_800x480.c`

### Shell long-press misclassification

- The original shell reproducer proved that synthetic short taps could be misclassified as long presses.
- Root cause for the shell path was that shell injection was routed through the same physical timing state machine as real buttons.
- That made the shell command vulnerable to unrelated scheduling/panel latency.

### Zephyr input subsystem behavior

- Without `CONFIG_INPUT_MODE_THREAD`, Zephyr processes input callbacks inline in `input_report()`.
- The `sync` argument is metadata on the event, not an async/sync execution switch.
- This was verified by reading Zephyr source in `subsys/input/input.c`.

### Shell path after semantic injection change

- Latest shell traces show that shell commands now produce deterministic `PRESS` events quickly, without being turned into `LONG_PRESS` by display timing.
- Example pattern observed after the semantic shell change:
  - `BTNTRACE shell press_send ...`
  - `BTNTRACE shell release_send ...`
  - `BTNTRACE enqueue code=... evt=0 ...`
  - `Button: BTN_X PRESS`
  - later, the slow display frame log appears independently

## What Is Still Not Proven / Still Open

### Real physical button path

- The shell fix does **not** prove the real hardware button path is correct.
- The remaining concern is whether the actual MCP23017 -> `gpio-keys` -> Zephyr input path has a delay or serialization point that could still hurt short presses.
- The user explicitly called out that a slow panel worker should mostly sleep on BUSY and should not by itself starve unrelated threads.
- That concern remains valid and unresolved.

### Next debugging target

- The next investigation should focus on the real button chain:
  1. MCP23017 interrupt behavior
  2. `gpio-keys` debounce timing
  3. input thread delivery under the current config
  4. any expander or GPIO-read serialization that could delay release recognition
